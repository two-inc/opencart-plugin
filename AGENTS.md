# Agent guide: Two for OpenCart

The Two payment extension for OpenCart 4.1 (floor 4.1.0.0, PHP 8.1+). It is a rewrite in progress: the structure is in place and features land phase by phase. Behaviour and copy follow the sibling plugins (PrestaShop is the reference for behaviour) under the Plugin Build Guide's Parity rule.

## Layout

The repo root is the extension directory: a shop serves it as `extension/two/`.

| Path | What lives there |
|---|---|
| `install.json` | OpenCart 4 extension manifest. Holds the one version string |
| `system/library/opencart/` | OpenCart 4 implementations of the core's ports (`DbSettingsStore`, which upserts; `CurlTransport`; `LogLogger`; `DbOrderRecords`, the `two_order` table; `DbRefundRecords`, the `two_refund` table; `EventSubscribers`, the order postprocessing event), `NoteText` (a core `Message` in a language) and `Services`, the one place the core graph is built |
| `system/library/core/` | The platform-neutral core: `Client`, `Environment`, `RecordProvider`, `SettingsProvider`, `SettingsSave` (the selective admin save), `Availability`, `OrderBuilder`, `Postprocessing`, `ErrorMapper`, `CustomHeaders`, `Brand`, `ApiKeyVerdict` (the key heartbeat), `OrderFlow` (create, confirm and cancel), `IdempotencyKey` (the key every write carries), `OrderLifecycle` (whole-order fulfil and cancel off the status maps, and the invoice), `OrderRefunds` (refunds and the credit note), `OrderEdit` (order-edit sync), `OrderRefused`, `PaymentTerms` (the terms offered and the default-term chain), `Surcharge` (the fee grid and its save rules), `FxRates` (Two's FX rates), `FeeQuote` (the fee quote) and `Message` (a merchant note as a language key), plus the ports they need (`SettingsStore`, `Transport`, `Logger`, `OrderRecords`, `RefundRecords`, `PostprocessingSubscribers`) and `SettingsOverlay` (read-only typed credentials for the live key check) |
| `admin/`, `catalog/` | Thin OpenCart 4 adapters: controllers, models, language files, templates, the payment terms fee order total (`total/two_fee`: `catalog/model/total/two_fee.php` and its admin page), and `admin/view/javascript/two_admin.js` (the live API key check). `catalog/controller/cron/two.php` is the daily merchant-record refresh, registered in OpenCart's cron table by install() and `configure.php`; `catalog/controller/event/two.php` is the order lifecycle, registered in OpenCart's event table the same way |
| `dev/` | `configure.php` (installs and enables the extension), the docker image, CI scripts (`ci/smoke.sh`), packaging, and the environment parity check (`environment-parity.php`, byte-identical in the four plugin repos; `environment-contract.php` and the generated `environment-contract.json`) |
| `tests/` | Offline PHP suite: `tests/*Spec.php`, run by `tests/run.php`. `tests/e2e/`: the Playwright suite, its compose file, the Two API stub (`stub/`) and the shop setup (`bin/`) |

## The core boundary

Core classes hold the rules and never call OpenCart: no registry (`$this->load`, `$this->db` and so on), no OpenCart classes or config constants, no database, network or file I/O, no `getenv` or request globals. Adapters read the shop and pass plain values in; anything the core needs from outside goes through a port interface the adapter implements. `tests/CoreBoundarySpec.php` enforces this, so a new core file must also be added to its type list.

OpenCart 4 autoloads `Opencart\System\Library\Extension\Two\Core\FooBar` from `system/library/core/foo_bar.php` (lower case, CamelCase split by underscores). `dev/autoload.php` applies the same rule offline.

Stubs throw `NotImplemented::inPhase(...)` naming the phase that implements them. Never replace one with a guessed return value.

| Command | What it does |
|---|---|

| `make test-js` | Jest over the checkout script and the company search host |
| `make lint` | `php -l` over every tracked PHP file |
| `make phpstan` | PHPStan level 6 against the OpenCart 4.1.0.0 sources (pinned, checksum-verified), then the core alone with no OpenCart symbols, then `tests/` (apart, since its DB double shares OpenCart's class name) |
| `make install` | Fresh docker shop (MariaDB plus OpenCart 4.1.0.4 from the upstream zip, installed with `cli_install.php`), extension installed and enabled |

| `make patch` / `minor` / `major` | bumpver, commits, no tag or push |

Settings come from `.env` only (see `.env.example`). `TWO_INTERNAL_ENVIRONMENTS` passes through to the shop.

CI (`.github/workflows/tests.yml`) runs lint and the suite on PHP 8.1 and 8.4, PHPStan, Jest (Node 20, jsdom) over `catalog/view/javascript/two_checkout.js` and the company search host, the install smoke and the package build. All are gates. `make test-js` runs Jest locally (`tests/js/`). `.github/workflows/environment-parity.yml` runs `php dev/environment-parity.php` (below). `.github/workflows/vendored-company-search.yml` checks the vendored company search modules against the Magento plugin's staging branch. `.github/workflows/e2e.yml` runs the E2E suite (below). The admin's live key check is still covered by the save-time rules it mirrors (`SettingsSaveSpec`) and the smoke.

E2E (`tests/e2e/`, `.github/workflows/e2e.yml`):

- The E2E shop is its own compose project (`tests/e2e/compose.yml`, the same image as `make install`) on 127.0.0.1:1240, so it runs beside the `make install` shop. `E2E_OPENCART`, `E2E_OPENCART_SHA256` and `E2E_PHP` pick the leg; CI runs 4.1.0.0 on PHP 8.1 (the floor, which voids an unplaced order on every checkout edit) and 4.1.0.4 on PHP 8.4, on every PR and push.
- The Two API stub (`tests/e2e/stub/two-api-stub.mjs`, Node, no dependencies) answers as `api.sandbox.two.inc` inside the compose network, over HTTPS with a throwaway CA the shop trusts (`bin/tls.sh`), so the extension runs unchanged with no host override. It mints the sole-trader signup's two tokens (each in Two's `two-delegated-authority-token` header, with the shop's key only), keeps orders in memory, replays a repeated Idempotency-Key, serves Two's hosted checkout on `TWO_API_STUB_PORT` (required, no default: the payment URL is built from it) and has control routes the specs use to inject a failure (refused and not applied, or applied with the connection dropped) and read what was sent and how it was answered. It applies Two's key and amount checks, with Two's status and error code and Two's tolerances: a merchant call without the shop's key (`TWO_API_STUB_KEY`) is 401, and an order, edit or refund whose amounts do not add up is 400 (signed, so a discount line counts against the order; a rounded unit price is taken as the exact one on an order, and on a refund only when it carries no tax subtotals, as Two does; a refund's tax subtotals add up to its amount plus prepaid amount; refund fields Two does not know are ignored). It models only these checks, not every rule Two applies.
- `bin/prepare.sh` installs the extension with `configure.php` (sandbox, the stub's key) and `bin/seed.php` drops the demo data's fixed-amount Eco Tax, which the extension refuses, makes GBP the store's currency for the UK buyer, as in the sibling plugins' E2E stores, and turns on the demo 10% coupon (2222). `bin/tls.sh` remakes the 30-day certificate when it has a day or less left.
- The specs place an order with company search, edit it in the admin before fulfilment, fulfil it (Shipped), refund part from the Two tab and the rest with the refund status, retry a refund Two did not apply and one Two applied but whose answer was lost (refunded once), check out with a coupon (a negative discount line), and cancel (Canceled), checking both the page and what the stub holds. `payment-terms.spec.ts` clicks each term chip (the stub's merchant record offers 30, 60 and 90 days, due in 30, so only a non-default case tells a chosen term from the default) and checks the `terms` of the POST /v1/order body the stub captured, for standard terms and end of month, and that a term withdrawn after it was chosen is refused with nothing sent. `two-api.spec.ts` shows the stub refuses a wrong key, an order whose amounts do not add up and malformed refunds, and accepts what Two accepts (a coupon line, a rounded unit price, a refund with a prepaid amount and a surcharge, a full refund with a revision), each beside its twin.
- The sandbox leg (staging pushes, nightly, and manual runs) places one order against Two's real sandbox with the `TWO_SANDBOX_API_KEY` secret, and is skipped with a notice without it. It passes the buyer's verification with Two's test endpoint `POST /test/verify_order/{id}` and fails with that call's status if the endpoint refuses.
- The upgrade smoke (`bin/upgrade-smoke.sh`, every PR) installs the newest release tag from 2.0.0 on, places an order, swaps HEAD in, re-runs `configure.php` and checks every stored setting is kept and an order still places. Until the first release of the rewrite there is no tag, and it skips, saying so; the 1.x tags are the OpenCart 3 extension.

Environment parity: `dev/environment-parity.php` extracts this plugin's Environment setting (values, default, dropdown, read path, labels, description and the shared case table's hash) from the code named in `dev/environment-contract.php` into `dev/environment-contract.json`, and compares it with the PrestaShop, WooCommerce and Magento plugins' snapshots, read with `gh api`. After changing the environment rules, the en-gb admin labels or the description, run `php dev/environment-parity.php --write` and commit the JSON. The script is byte-identical in all four repos: change it in all four together.

The docker shop mounts the repo read-only, because OpenCart's Installer > Uninstall deletes everything under `extension/two`.

## Staging shops

The staging shops deploy this repo to `extension/two` on every new commit and then run `php <checkout>/dev/configure.php`. So `install.json` must stay at the repo root, and `configure.php` must stay idempotent and safe to run on every commit. The shops also serve the whole repo, so every CLI entry point refuses web requests (`PHP_SAPI` guard) and the root `.htaccess` refuses everything except the runtime paths. The package ships only `install.json`, `admin/`, `catalog/` and `system/`.

## Languages

Every string the admin or the buyer sees comes from the language files: `admin/language/<code>/payment/two.php`, `admin/language/<code>/total/two_fee.php` and `catalog/language/<code>/payment/two.php`, and the merchant notes in `payment/two_notes.php`, for en-gb (the reference) and nb-no, sv-se, nl-nl and es-es. Twig takes its copy from the controller, and the checkout script from the `i18n` block of its JSON island (the `js_*` keys); neither holds English of its own. Copy is in sentence case, with no em-dashes.

- Wording follows the reference plugin's catalogues wherever the English source matches, so buyers read the same text in every plugin; strings the reference does not have were translated for this plugin and want a native speaker's check.
- `tests/LanguageCatalogueSpec.php` is the completeness gate: every en-gb file exists in every locale with exactly en-gb's keys, every value filled in, and the same placeholders (`%s`, `%d`, `%1$s`, `{name}`; numbered ones in any order, the rest in en-gb's order), and no bare `%` where en-gb has none, since sprintf throws on one. It also refuses a prefixed language load read from the loader's answer. Add a key to en-gb and every locale in the same change. A new locale goes in the spec's list.
- The payment method title defaults per language (`text_title_default`, in both the admin and the catalog file) when the merchant has set none.
- OpenCart loads en-gb first and the shop language's file over it, so a shop language outside the five reads en-gb. For the same reason `$this->load->language()` returns en-gb's copy: read a prefixed load back with `$this->language->get()`, as the method title and the fee line do.
- Merchant notes (order history lines and the refund form's outcomes) are `Message`s from the core: a key and its parameters, with the English in `Message::TEMPLATES`, which the en-gb `payment/two_notes.php` must match key for key (the gate checks). `NoteText` renders them: history lines in the language of the order's store (`NoteText::shopCode`, its `config_language_catalog`), whoever changed the status, and answers on the admin page in the admin user's (`NoteText::adminCode`, `config_language_admin`). Both are language folder names (en-gb, nb-no); never pass default.php's `code`, which is the HTML lang (en, nb) and names no folder (NoteTextSpec checks). The notes file is one per language under `catalog/`; the admin file of the same name loads it. Log lines stay English, and Two's own error text goes into a note as a parameter, untranslated (`ErrorMapper::noteReason`, whose own wording when Two was not reached is a `Message`). The plugin's own text never does: why an order or a refund could not be built is an `OrderRefused` carrying a `Message` (a `refusal_` key), passed as a parameter of the note that says so and rendered in the same language. `OrderRefused` takes only a `Message`, so PHPStan refuses English text there.
- The order is placed with no history comment, since OpenCart mails the placing comment to the buyer; the Two note is a separate history line, not notified.

## Admin settings

The settings page has PrestaShop's five tabs: status, environment, API key and sort order (General), the per-language title and the checkout fields (Checkout fields), the payment terms and the surcharge (Payment terms), the fulfilment, cancel and refund status maps (Order management) and Diagnostics. Settings still to come say so on their tab.

- The save is selective (`SettingsSave`): a refused field keeps its stored value and is named, and the rest are written. The API key and environment are one pair, written together or not at all. A rejected key is never stored, and a key Two could not judge never replaces one that last verified.
- The API key is never sent back to the browser. An empty key field means "keep the stored key".
- Reading the merchant record refreshes it when due (`RecordProvider::refreshIfDue`), so a shop with no crontab still gets one.

Where OpenCart deliberately differs from PrestaShop, the row goes in `docs/divergences.md` until it is filed in the Build Guide's register.

## Checkout and order flow

The buyer picks Two, captures the company (below) and confirms. `catalog/controller/payment/two.php` maps the stored order through the model into `OrderFlow::create`, which builds the payload (`OrderBuilder`), runs the order postprocessing event (`Postprocessing`), creates the Two order and answers with Two's payment URL. The OpenCart order stays unplaced (status 0) until Two confirms it. Two then sends the buyer to `two.confirmation` (the order moves to the shop's default order status, then the success page) or `two.cancel` (the order stays unplaced with a history note, and the buyer is back at the cart with a notice).

- Tax: the plugin reports the shop's stored nets, taxes and rates and never computes or adjusts a tax. Where OpenCart keeps no per-line tax (shipping and other charge totals) the shop's own tax engine gives it, and the default handler refuses the order unless the lines add up to what the shop charged. A discount's tax is what the stored tax total leaves; at mixed rates, or with a fixed-amount tax rate, the order is refused rather than guessed.
- Every write request to Two (POST, PUT, PATCH, DELETE) carries an `Idempotency-Key` built by `IdempotencyKey`, whether or not the endpoint reads it today, and `Client` refuses one without. The key names one operation from durable ids: `create_<shop order id>_<start of the attempt's token hash>` (one per checkout attempt, so a new attempt on the same cart never shares one), `confirm_`, `fulfil_` and `cancel_` plus the Two order id, `edit_<two order id>_<hash>`, `refund_<two order id>_<refund row id>`, `refund_remainder_<two order id>_<hash>` (see Order lifecycle) and `fee_<payload hash>` (the fee quote, a pure calculation). It is logged with the request.
- Every order request goes through `Postprocessing::apply` in `OrderFlow`; `tests/CallSiteAllowlistSpec.php` fails a request that bypasses it. The README carries the merchant contract.
- Confirm checks the order against the Two order: create stores the sent payload's hash, and confirm rebuilds it from the stored order (hook included) and refuses, cancelling the Two order, on any difference. OpenCart rewrites an unplaced order on every checkout render, so the cart can change after create.
- Rates come from OpenCart's own tax engine set up for the stored order (`OrderTax`: its customer group and addresses and its store's settings over the default store's), never from the request's session, so a callback without the cookie and the admin rebuild alike. The smoke checks a non-default group's rate through the real engine (`dev/ci/order-tax-probe.php`).
- Callbacks for one order are serialised with a MySQL named lock, so the status read before `addHistory` cannot go stale. A guarded UPDATE would not do: `addHistory` keys the order mail and stock off the old status. The lock is released before every redirect (`Response::redirect` exits, so a finally would not run). A hit that waits out the lock (30 s) goes to the success page if the order is placed by then, otherwise to a neutral still-confirming notice, never the failure sentence.
- Unplaced means status 0 or the shop's void status, which OpenCart 4.1.0.0 sets on every checkout edit. A second callback hit on a placed order writes nothing; the status is read again before any write (`OrderFlow::afterCallback`).
- install() and `configure.php` rename a `two_order` table of another shape (the pre-rewrite extension's) aside before creating the table, and an order create is refused unless its token row was stored.
- The callbacks are guarded by a per-order token (its hash in `two_order`). OpenCart's session cookie is SameSite=Strict by default, so a callback arriving without it bounces once through a same-site page rebuilt from the route and the validated id and token.
- Refusals: the buyer gets `ErrorMapper`'s copy (section 6.4), the merchant's order history and the log get the reason.

## Checkout capture

- Availability (Build Guide section 18): the method list runs `Availability::withholdReason` over the session's cart, in order: enabled, API key, a merchant record that names the merchant (its short name; until then every restriction it carries is unknown), the key heartbeat (only a definitive rejection withholds; an outage falls through to the cached record), buyer countries from the merchant record (absent is unrestricted; empty or malformed allows none), the cart currency (NOK, GBP, SEK, USD, DKK, EUR), the buyer's country (billing, else shipping) on that list, a resolvable country when the search sits in the tile, then the minimum order, then the fee quote. The minimum has a platform floor (the record's amount, currency and basis; fails closed when it cannot be judged) and the merchant's own (Checkout fields tab, in the shop's default currency, on its basis, else the platform's, else gross; never withholds when it cannot be judged). OpenCart keeps amounts in the default currency, so the floor is judged there and converted at Two's FX rates (`FxRates`: `GET /refdata/v1/fx-rates`; every conversion refreshes a table older than 6 hours, retried 5 minutes after a failure; the last good table is served for as long as no refresh succeeds, and only a table never fetched fails closed; the health row shows its age). The fee-quote gate withholds a cart whose fee cannot be quoted: a fixed fee or cap with no rate into the cart currency, or a failed quote for the term the cart would be charged, rather than charge nothing. A withheld method is silent for the buyer and logged once per request. The General tab's health row names the first cart-free reason (the currency only when none of the shop's enabled currencies is usable), or the per-cart constraints and the last fee-quote failure.
- Company capture (section 1.1): the shared company search, the same control the sibling plugins ship. `catalog/view/javascript/two/` holds the four framework-free modules vendored byte for byte from the Magento plugin's staging branch (`company-search-panel.js`, `company-capture-component.js`, `company-identity.js`, `sole-trader.js`; never edit them: change the shared source and re-vendor with `dev/ci/vendored-company-search.sh --write`, which `.github/workflows/vendored-company-search.yml` runs as a drift check on every PR and nightly, using the base branch's copy of the script, so a PR cannot change the script it is checked with, short of editing that workflow, so a reviewer must check any change to it) and `company-search-host.js`, this extension's host for them: the search transport over the shop's relay, through the call queue like every other relay call (3 characters, 300 ms debounce, 30 s timeout, answers cached per country and term for 5 minutes, a degraded answer never cached, a 429 parks that control alone), OpenCart's address fields, and a `MutationObserver` that re-mounts after OpenCart re-renders a form. `catalog/view/stylesheet/two_checkout.css` is its look. The `catalog/view/checkout/checkout/after` event (`catalog/controller/event/two_checkout.php`, `Services::CHECKOUT_EVENT_*`) adds the stylesheet, the modules, `two_checkout.js` and the settings as a JSON island. The placement switch decides, alone, where the one control mounts: on each address form's own company field (`#input-<role>-company`, `payment` and `shipping`, each with its own identity and panel) or on the tile's one field (`#input-two-company`, the billing country, rendered only in tile placement, with no manual entry). Never both, and never by what was captured. The modes are Registered company, Sole trader (offered when the registry's company types for the country include `SOLE_TRADER`) and Enter manually (address placement only, the name only: placement then refuses for want of a company id, as the references do). Enter manually keeps the name in the field and saves it at once with no number. A Sole trader click clears nothing: until a sole trader is adopted the role is saved as the capture the click left, never as `sole_trader`, so a reload cannot restore an adoption that never happened. A sole trader's address and phone follow PrestaShop's rules: a blank writes nothing, a field the record leaves out is cleared only where it still holds the plugin's write, and the zone is filled only where it is unanswered or plugin-written. A blocked signup popup draws one button over the popover (`js_sole_trader_signup`), whose click opens it (TWO-26775). A pick with no number takes it from `/companies/v2/company/{lookup_id}`; with "Autofill company address" (Checkout fields, on by default, address placement only) the same call fills that form's street, city, postcode and zone, and a country change clears only fields still holding what was written. Two's own `TWO:` numbers are never shown. Each control saves its capture per role in the session (`save_company`). A saved address keeps its capture in its own `custom_field` (`two_company`), written by the `addAddress` and `editAddress` before events (`Services::ADDRESS_EVENTS`), and the admin's customer address edit keeps it (`admin/model/customer/customer.editAddress/before`, whose form posts only the configured custom fields), so a checkout on it reuses the capture; a capture saved before its number arrived gets the number when it lands (`CompanyCapture::topUp`); with none, the tile links to OpenCart's own address edit form (`account/address.form`), which hosts the same control (role `account`). The buyer's role is the tile, else billing when the shop collects it, else shipping. `two_checkout.js` runs every call one after another, Confirm included, since OpenCart writes the whole session back at the end of every request, even one that only reads it. A search, a company lookup and confirm skip an order intent ahead of them (the intent writes only its own rate-limit stamps) but wait for every other call. Relay calls are abandoned after their timeout (20 s, the intent 40 s); confirm has none, as a form post would not. Confirm disables its button on the first press, waits at most 15 s for pending saves (not the tile's intent: confirm asks its own), and sends one confirm. On the shop, confirm holds the order's named lock (`DbOrderLock`, the callbacks' lock name), so a second confirm for the same order is refused while the first runs (`OrderFlow::exclusively`), never run alongside it. The vendored modules' own calls (covered countries, company types, the sole-trader token mint) cannot join the queue, so those routes, the search and the company lookup read the stored session again after their relay call and before keeping anything (`CompanyCapture::relay`): a request's write-back at shutdown never puts back a session older than a save that landed meanwhile. When the tile renders, every control saves its capture again, forced, before the intent. The shop relays every call (`CompanyLookup`, 30 s) behind a per-session token and the reference plugin's rate limits (`RateLimiter`: per caller and action in the `two_rate_limit` table, counted in one atomic upsert, expired rows pruned, answering 429; and five intents a minute per session). The caller is the socket address from the server environment, never REMOTE_ADDR, which OpenCart's startup overwrites with the client-sent Client-IP header; behind the merchant's Trusted proxies (Diagnostics) it is the nearest X-Forwarded-For hop that is not one of them. Diagnostics > Disable checkout rate limiting (off by default) removes the per-caller ceiling only, as a stopgap until Trusted proxies is filled in.
- Payment terms (section 4): the terms come from the merchant record (`available_terms`), never from a list the plugin holds; the Payment terms tab only narrows them (the ticked terms, 30, 60 and 90 days on a fresh install as in PrestaShop, and the term type: end of month offers 30, 45 and 60 only). With no term offered Two is withheld (`no_terms` on the health row). The default chain (`PaymentTerms::defaultTerm`): a single offered term, else the merchant's default, the record's `due_in_days`, 30 days, each only when offered, else the shortest. The tile shows the offered terms as chips, an ARIA radiogroup with one tab stop, arrow keys, Home and End (a single term is shown, not chosen). A choice takes its place in the call queue at once (arrow keys hold it 250 ms so a run of keys saves once, and a Confirm meanwhile waits behind it), then goes to `two.term`, which refuses a term the record does not offer and keeps it in the session, and reloads OpenCart's own confirm view (which rewrites the unplaced order), swapping in only its totals rows. Each chip shows its term's fee from `two.fees` (tax included when the shop shows prices with tax, `config_tax`; a failed quote shows none): the terms are quoted in parallel within 10 s, quotes are kept in the session by request hash for 60 s, and the call reloads the stored session before keeping them, so its write-back never undoes a term saved meanwhile. The chosen term is cleared from the session when the order is placed. An admin order edit runs in a fresh API session, so there the term is the one stored with the order (`two_order.payment_terms`), and the fee gate does not apply. The order carries the `terms` block; it is stored on `two_order.payment_terms` so the confirm and edit rebuilds book the same term. Placement (`placementTermRefusal`, run in confirm under the order's lock, before the intent) refuses an order when the record offers no term, the session's term is not offered, the fee cannot be quoted, or the stored order's fee is not the fee for the term.
- Payment terms fee (section 5): the merchant's grid (Payment terms tab: method, total fee or fee difference, line description, rounding, a per-term percentage, fixed fee and cap) is sent as `buyer_fee_share` to `POST /v1/pricing/order/fee`, which computes the fee; the answer's `buyer_fee_share` is the fee's net. Fixed fees and caps are in the shop's default currency and converted at Two's FX rates; no rate fails closed. The quote has no side effect, so its key is `fee_<payload hash>`; one 30 s timeout serves the gate and the charge, and answers (a failure included, so an outage costs one wait) are reused from the session for 60 s while their request is unchanged. Two is asked only from the checkout's own requests: elsewhere (the header cart on every page) the fee shows only when a quote is already held. The fee is an OpenCart order total, `two_fee` (sort order 4, before Taxes), added while Two is the chosen method: its net from the quote, its tax what the shop's tax engine gives the tax class the merchant selects (required while a surcharge is on; a 0% class leaves it untaxed). The plugin never picks a rate. The order builder sends it as a SERVICE line from the order's own totals, its tax and rate from that class (`OrderTax`), as for handling. install() and `configure.php` install and enable the total (install() puts it before Taxes and logs when Taxes sorts too early for that); uninstall removes it. With a surcharge set and the total not enabled, Two is withheld (`fee_total_off` on the health row). An order's fee is the fee it was placed with, as PrestaShop replays a placed order's fee rows: create stores it on `two_order` (`payment_fee`, and `placed_fee`: the order's currency code and currency value, and for an order with a fee its title, net, tax, rate and tax rows). An admin edit never quotes: it puts the placed fee line back, kept in the order's currency so a re-stamped rate cannot move it, with its own tax rows and their names (none for an order placed without one), and the rebuild sends its stored tax and rate, so OpenCart's saved order and Two's payload agree whatever the surcharge, terms or quotes now say. A rebuilt order placed with a fee that no longer carries one (the fee total disabled) is refused with a history note. An order whose currency an edit changed from the one it was placed in (`FeeQuote::placedInOtherCurrency`) is refused, as PrestaShop refuses a currency change on a Two order: the edit sync and the fulfil check judge it before the rows hash (OpenCart keeps rows in the default currency, so a currency-only edit leaves them alike), each with a history note saying to switch the currency back, and nothing goes to Two until it is. The confirm refuses it too, without that advice. OpenCart's own totals show the fee at its worth in the new currency (the placed net over the placement's currency value), never the placed figures relabelled. The confirm judges the fee the same way, so a surcharge switched on while the buyer is at Two's checkout does not refuse the order.
- Optional fields (section 6.1): invoice email, PO number, project and department in the tile, each with its toggle (default on). They go on the order create (`invoice_details.invoice_emails`, `buyer_purchase_order_number`, `buyer_project`, `buyer_department`) and are kept in `two_order.buyer_fields` so the confirm rebuilds the same payload.
- Order intent (section 6.3): built server-side from the stored order by the order builder and the hook (`order_intent`), never in the method list. The tile asks it once Two is chosen and the company is known, and shows the brand's approved or declined notice; confirm re-checks the currency and buyer country (OpenCart keeps the chosen method through a switch), asks the intent again, and creates the order only on an approval (`OrderFlow::afterIntent`): a decline, no answer, an error or an answer without a decision refuses placement with the reference plugin's buyer sentences. Its key is `intent_<session hash>_<payload hash>`; with no session nothing is sent. Sole-trader mints are keyed `soletrader_<token>_<session hash>_<attempt>`, one attempt per click.

## Order lifecycle

Once placed, the order's Two order follows the merchant's status maps. One catalog event, `catalog/model/checkout/order.addHistory/after` (`Services::EVENT_*`), runs `catalog/controller/event/two.php`, which hands the shop to `OrderStatusEvent` (`system/library/opencart/`, specced offline) after every status change: the admin's (OpenCart runs the catalog order model in a store instance, events included), the storefront's and the extension's own. OpenCart's order edit writes the edited rows and then adds a history line, so the same event sees edits. Orders paid with another method, and unplaced orders (status 0 or the shop's void status, so a refused confirm's note can never cancel a live Two order), are left alone.

- Each event first syncs any edit (below), then acts on the status: a mapped fulfilment status fulfils the whole Two order (`POST /v1/order/{id}/fulfillments`, through the hook as `capture`), the mapped cancel status cancels it, the mapped refund status refunds what is left. A status in more than one map takes the first of fulfil, cancel, refund.
- Idempotent: the stored Two state, then Two's live state, decide whether anything is sent, so a repeated event or a re-save sends nothing. A fulfil marks the order FULFILLING before reading it back. FULFILLING, FULFILMENT_NEEDS_MANUAL_RESOLUTION, FULFILLED, DELIVERED and REFUNDED all count as fulfilment asked for. Every write also carries an `Idempotency-Key` (`fulfil_<two order id>`, `cancel_<two order id>`), though Two honours it today only on partial fulfilments and refunds. Empty bodies go as `{}`: Two refuses a JSON list.
- Before fulfilling, the order's own rows (products with price, tax and quantity, totals, and the billing and shipping addresses as stored on the order) must hash to `rows_hash`, kept when Two confirmed the order and moved on by every edit Two accepts. Nothing from the catalogue or the tax setup is used, so a deleted product or a rate change never blocks a fulfil. On a difference (an edit Two refused or never got) nothing is sent and the history says so. An order with no `rows_hash` (placed before it was kept) is refused with a pointer to the Two merchant portal, never fulfilled unchecked. `rows_hash` and `edit_key` are added in place by install() and `configure.php`.
- The status change is never undone. Every outcome except "nothing to do" goes in the order history at the status the merchant chose (a second `addHistory`, guarded so it does not re-enter the handler), and every refusal in the log. A fulfilled order is not cancelled: the note says it needs a refund.
- Order-edit sync (`OrderEdit`): when the rows no longer hash to `rows_hash`, the order is rebuilt and its create payload hash compared with `payload_hash`; on a difference the edit goes as `PUT /v1/order/{id}` through the hook as `order_update`, while Two holds the order VERIFIED or CONFIRMED. The key is `edit_<two order id>_<hash of the last accepted edit's key (the create key for the first edit) and this payload>`; each accepted edit stores its key, payload hash and rows hash. An unknown outcome (no answer, a 5xx) clears `payload_hash`: the next save then sends the order as it stands whatever its rows (even edited back to what Two last accepted, since Two may hold the lost edit), under the same key while the order is unchanged, and fulfil refuses until Two has accepted it. An edit Two refuses as such (400 or 422) keeps its rows hash (`edit_refused_hash`), so the same edit is not resent or noted on every save; a different edit is. A 408 or 429 counts as no answer, and another 4xx (a key being changed, a conflict) records nothing, so the next save resends. A fulfil blocked this way says to fulfil in the Two merchant portal if the edit cannot be sent. After fulfilment (or once Two reports the PARTIAL status) an edit is refused with one note per rows hash, never sent, whatever an earlier edit's outcome.
- Refunds (`OrderRefunds`): Two refunds an order it holds as FULFILLED, DELIVERED or REFUNDED. The refund status refunds what Two's order total leaves after the refunds Two already holds: an empty body when there are none, else one line per tax rate from Two's tax subtotals less its refunds'. Its key is `refund_remainder_<two order id>_<hash of Two's prior refund ids and the amount>`. The Two tab's form refunds picked quantities of the Two order's lines (each the line's own net and tax share, referenced by its id) and an amount line (net and tax typed, at one of the order's rates). Each form refund is a `two_refund` row created before the call, keyed `refund_<two order id>_<row id>`. A line's quantity is capped at what earlier rows (done, unknown or never settled) left of it, and the last of a line takes the net and tax they left. Refunds on one order are serialised with a MySQL named lock (`RefundRecords::lock`, named from the order id and a hash of the database and table prefix), so a status-map refund and a form refund never both pass the checks. Section 12.2.1: a line with a net amount but no tax at a taxed rate is refused, and nothing more than remains is sent.
- After every refund Two's refunded total is read back. A rise of at least the amount sent is done; a 2xx with a smaller rise means Two answered with an earlier refund under the key and nothing was applied; no answer (a timeout, a network error, a 5xx) with no rise marks the row unknown. While a row is unknown (or never settled), every other refund, the status map's included, is refused until the row is retried from the Two tab: the retry sends the stored payload under the stored key, so Two applies it at most once, and counts the earlier attempt as applied when Two answers with a refund it already held, or when Two answers the retry and its refunded total has risen by the amount since the first attempt (kept on the row as `refunded_before`); a rise with no answer leaves the row unknown, since it could be a refund made in the portal. Every outcome goes in the order history, and a refund Two applied is logged with its key at info level. A retried full refund (a body with no amount: empty, or with only fields a hook added) is judged against what remains at Two now, since a refund made meanwhile in the portal lowers what Two refunds; with nothing left it is not sent, and the row settles done with a note that nothing was left (the earlier attempt or a portal refund took it); an explicit amount over what remains is still sent under its key, so Two either answers with the earlier attempt or refuses it. A partial row left without its key (the request stopped between the insert and the key) gets it rebuilt from its row id on retry. The amount checked is the hooked body's when it names one, else the plugin's own.
- The admin order page has a Two tab. OpenCart renders the payment extension's `order()` inline with the page, so it is only a shell (`two_order_tab.twig`): the content loads from `two.panel` when the tab is opened, with a loading line and an error line if the shop does not answer, so a slow or unreachable Two never holds up the order page. The content is read with the order's own store settings. It reads Two for any linked order not cancelled, whatever state was stored (a fulfil read back as FULFILLING, or a fulfil in the merchant portal, leaves a stored state nothing else refreshes), and opens the refund form on Two's live state. It shows the Two order id and state, Two's refunded total and what is left, the refund form, the refunds sent from the shop (with Retry on an unknown one), and the invoice and credit-note downloads. The refund and retry forms post through a small inline script in `two_order.twig`, which shows the outcome and reloads the tab (`two.panel`) whatever it was, so the form and figures are never stale. The downloads (`two.invoice`, `two.creditNote`) sit behind the admin login and its user_token and also need access to Sales > Orders and the extension; the refund and retry actions need modify rights on both. The admin registers only admin/ and system/ event triggers, so refund and retry run on the order's store instance's events (`catalogEvent()`, as OpenCart's own admin order edits do, with `config_store_id` set to the order's store), where the order postprocessing subscribers are; `CallSiteAllowlistSpec` holds every admin write to that. The invoice is asked for as the original streamed by Two (`?v=original&proxy=true`), since Two may otherwise answer with a redirect and the transport does not follow redirects; on Two's `ORDER_NOT_FULFILLED` it reads the order's state: still fulfilling says try later, another state is named, and a just-fulfilled order is asked once more. The credit note is the latest, streamed by Two (`/v1/credit_note/{id}/pdf?proxy=true`). Only a real PDF is served.
- Partial fulfilment is not offered from the shop, as in PrestaShop: the merchant fulfils part of an order in the Two merchant portal. OpenCart has no shipment or invoice record to key one on, and Two splits a partly fulfilled order into child orders that refunds and invoices would then have to follow. The plugin reads Two's PARTIAL status and refuses edits once it is set.
- A re-create (the buyer confirms the same OpenCart order again) cancels the earlier Two order before its id is overwritten, and refuses the new one if Two still holds the earlier one open.
