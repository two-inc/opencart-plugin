# Divergences from the reference plugin

Rows waiting to be filed in the Build Guide's divergence register (filed at P13, the release phase). PrestaShop is the reference for behaviour. Each row gives where the two plugins differ, what each does, and why.

| Area | PrestaShop behaviour | OpenCart behaviour | Reason |
|---|---|---|---|
| Admin, General: API key save | Saving the General tab verifies the submitted key against the submitted environment. A key Two rejects (401 or 403) is reverted to the stored key, but the environment is saved anyway. Any other failure (no answer, a 5xx) stores the submitted key with a warning. | The key and environment are one pair, saved together or not at all. A rejected or malformed key is never stored. A key Two could not judge replaces the stored key only when the stored key's last definitive answer from Two was not ok, so an outage during a save never swaps a verified key for an unverified one. | A key is only good against the environment it was issued for, so saving one half of a refused pair leaves the shop with credentials that cannot work. Keeping a verified key through an outage keeps Two at checkout. |
| Admin, General: API key field | The stored key is rendered back into the form. | The key field always renders empty, with a note that a key is saved. An empty field means "keep the stored key", and the live check then uses the stored key. | The key never needs to leave the server, so it doesn't. |
| Admin, Diagnostics: custom request headers | Rows are refused for an invalid name, a reserved name, a missing value or an invalid value. A second row with the same name is saved. Server-side calls then send both header lines; the browser-side header map keeps only the last row with that name. | The same four checks, plus a second row with a name already used is refused on save. | OpenCart's client sends the first row with a name and drops the rest, so a duplicate would be saved but not sent. A row the merchant sees saved should be a row that is sent, the reasoning PrestaShop applies to a row with no value. |
| Admin copy: environment help, title help, key help | Environment help names Production and Staging. Title help reads "which is appear on checkout page". Key help says "api key". The fulfilment help leaves a bracket unclosed. | Environment help names Production and Sandbox. The grammar, the capitalisation of "API key" and the bracket are fixed. | Merchants test against sandbox; staging is offered only on internal Two shops. The rest are typo fixes. |
| Order payload: shipping and charge tax | The carrier's stored tax amounts give the shipping line's tax. | OpenCart stores tax per product line and per rate for the order, but none for shipping, handling or the low-order fee. Those lines take the tax the shop's own tax engine gives their stored tax class at the order's addresses, and the default handler refuses the order unless the lines add up to the tax and total the shop charged. | It reproduces the merchant's own computation, the one OpenCart made at checkout, and is checked against what the shop actually charged, so the plugin never invents tax. |
| Order payload: discount tax | A cart rule is split across the rate contexts of the lines it applies to. | Coupon and reward-point discounts go as one line whose tax is what the shop's stored tax total leaves once every other line is counted. When the taxed lines carry more than one rate, the order is refused and the log names the reason. | OpenCart does not store how much of a discount's tax fell at each rate, and apportioning it would be the plugin deciding how tax is levied. |
| Order payload: fixed-amount tax rates | No equivalent: ecotax goes as its own line with a rate. | A line whose tax class holds a fixed-amount rate is refused, and the log names the line ("fixed-amount tax rate on <line>"). | A Two line carries one percentage rate, so Two would refuse the line; the plugin does not send what it knows will be refused. |
| Buyer cancels at Two's checkout | The order moves to the cancelled status map. | The Two order is cancelled and read back; the OpenCart order stays unplaced (status 0, a missing order) with a history note, and the buyer is back at the cart with the same cart. | Moving an OpenCart order off status 0 sends the buyer the order confirmation email, and an order the buyer never placed should not be announced as cancelled. |
| Confirmed order status | A merchant status map for verified orders. | The shop's default order status (Settings > Option > Order Status) until the Order management tab gains the field. | Interim: the core flow ships before the full status map set. |
| Callback session | The callbacks read the session as it arrives. | A callback that arrives without the session cookie answers with a page that reloads it from the shop itself, keeping the per-order token check on that final hop. The target is rebuilt from the route and the validated order id and token, so it cannot redirect elsewhere. | OpenCart 4.1's session cookie is SameSite=Strict by default, so the redirect back from Two carries no cookie, and OpenCart would otherwise replace the buyer's session (cart and login) with an empty one. |
| Fulfil of an edited order | Order edits are synced to Two, so the order fulfilled is the order as edited. | Order edits are synced to Two the same way. Before fulfilling, the order's own rows (products, totals and addresses as stored on the order) are also compared with a hash kept when Two last accepted them, so an edit Two refused, or one whose outcome is unknown, blocks the fulfil until Two accepts the order as it stands, and the order history says why. | OpenCart has no record of whether an edit reached Two other than the plugin's own, and fulfilling would otherwise invoice an order the merchant has since changed. Only data the order owns is compared, so catalogue or tax changes never block a fulfil. |
| Fulfil and cancel outcomes | The outcome goes to the module log. | The outcome also goes in the order history, at the status the merchant chose, without undoing the status change. | The merchant works from the order page, so a refused fulfil or cancel should be visible there, not only in a log. |
| Partial refunds | A credit slip made on the order page is sent to Two as a partial refund, keyed on the slip. | OpenCart has no credit memo or slip. The Two tab on the order page has a refund form: quantities of the Two order's lines, and an amount line with its net, tax and rate typed. Each refund is a row in the plugin's own table, created before the call and keyed on its id. | The platform has no refund record to hang one on, so the plugin keeps its own. |
| Refund with an unknown outcome | A credit slip is sent once, keyed on the slip; one the module does not send is reported on the order page as not sent. | The refund row is marked unknown and every other refund on the order, the refund status map's included, is refused until the merchant retries it from the Two tab. The retry resends the stored request under the same key. | A second refund made from the form would carry a new key, so Two could refund twice. Retrying under the same key lets Two apply it at most once. |
